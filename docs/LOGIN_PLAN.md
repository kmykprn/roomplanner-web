# 作業手順書: Google ログインの導入

匿名認証のままだと**サイトデータを消した時点で uid ごと消え、それまでのデータに
二度と到達できない**。Safari は7日間使わないだけでこれが起きる。

サーバーに保存しても uid が変わってしまえば「自分のものがどれか」が分からないので、
保管機能（作った家具の一覧・部屋のサーバー保存）より**先に**ログインを入れる。

課金とは独立して着手できる。ログインは課金の土台にもなるが、
課金の判断が決まっていなくても進められる。

## 全体の順序のなかでの位置

| | やること | 決済の判断 |
|---|---|---|
| **1** | **ログイン導入（この手順書）** | 不要 |
| 2 | 保管（家具一覧・部屋のサーバー保存） | 不要 |
| 3 | 生成前のログイン必須＋サーバー側で匿名トークンを拒否 | 不要 |
| 4 | 通算の無料回数カウンタ＋決済 | 必要 |
| — | 許可リストを外す（一般公開） | 4 のあと |

**許可リスト（`ENFORCE_ALLOWLIST`）を外すまでは、無料枠が破られる心配はない。**
いまは `POST /jobs` の入口で `_check_allowed(uid)` が弾いており、
登録された uid 以外は1回も生成できない。

### やってはいけないこと

**匿名アカウントに無料回数を持たせない。** 匿名 uid はシークレットウィンドウや
サイトデータ削除でいくらでも作り直せる。無料枠をそこに置くと無限に増やせてしまい、
しかも1回あたり約 ¥39 の GPU 実費が出ていく。

無料回数の導入は、ログイン必須化（順序 3）と**同時**に行うこと。

## iOS ではポップアップではなくリダイレクト（2026-09-13 追記）

iOS Safari は `linkWithPopup` の結果を持ち帰れず、Promise が決着しないまま止まる（実機で再現）。
根本原因は `authDomain` がアプリと別オリジンだったこと。Safari 16.1+ などはサードパーティの
保存領域を分断するため、ポップアップもリダイレクトも壊れる。

対処は 2 段:

1. `authDomain` を `kmykprn.github.io` にし、Firebase のヘルパーを同じオリジンで配る
   （`kmykprn.github.io` リポジトリ、`docs/OPEN_ISSUES.md` の 2）
2. iOS では `linkWithRedirect` で遷移し、戻ってきた起動時に `getRedirectResult` で受け取る
   （`auth.ts` の `receiveRedirect`）。**匿名ログインより先に受け取る**。2 台目の
   `credential-already-in-use` は `googleLink.ts` の `finishRedirect` がポップアップと同じ分岐で処理する

リダイレクトはページを読み直すので選んでいた写真は持ち越せない。`redirectLogin` ストアで
画面に伝え、選び直しを促す。PC はポップアップのまま。

## 昇格（linkWithPopup）とは

全員が最初からログインしているわけではない。**誰もログインしていない状態から始まり、
必要になった人だけが後からログインする。**

```
初回アクセス → 匿名アカウント作成（uid: AbCdEf...）→ ブラウザに保存
        ↓ linkWithPopup で Google を紐づける
同じアカウント（uid: AbCdEf... のまま）＋ Google
        ↓
別端末で Google ログイン → 同じ uid に到達できる
```

**uid が変わらないことが肝。** それまでに作ったデータも、サーバー側の許可リスト登録も
そのまま引き継がれる。`signInWithPopup` を使うと別の uid でログインし直しになり、
全部が切り離される。

## 先に潰す必要がある構造上の問題

### ① `ready` が1回きりの Promise で固まっている

`src/platform/auth.ts`:

```ts
const ready: Promise<User> = auth ? watchAuthState(auth) : Promise.reject(...);
```

`getUid()` も `getIdToken()` もこの `ready` を待つ。**一度解決するとその `User` を持ち続ける。**

`linkWithPopup`（1台目）は同じ `User` オブジェクトを書き換えるので問題ない。
**しかし2台目のフォールバックで `signInWithPopup` を使うと、Firebase の現在ユーザーが
別オブジェクトに差し替わる。** `ready` は古い匿名ユーザーを掴んだままなので、
`getUid()` が古い uid を返し、`getIdToken()` は失効したユーザーのトークンを返す。

→ 手順2で「今のユーザーを追う」形に作り替える。

### ② ログインのポップアップはブラウザに塞がれる

ポップアップは**直接のクリックからしか開けない**。`await` を挟んだあとでは塞がれる。

```ts
startButton.addEventListener('click', async () => {
  const files = await pickImages();      // ← ここでユーザー操作の文脈が切れる
  if (files.length > 0) void startGeneration(files);   // → ensureRegistered()
});
```

**`ensureRegistered()` が自分でポップアップを開くのがまずい。**
ログインを求める画面を出し、**その画面のボタン**で開くなら成立する。

「ログインを動線から切り離す」という意味ではない。手順3の動線を参照。

## 手順2: `auth.ts` を作り替える【完了 #36】

`ready`（1回きり）を、**現在のユーザーを保持する形**に変える。
分岐は `src/platform/googleLink.ts` に切り出し、偽の関数で両方の道を検証してある。
2台目のログインし直しは、失敗した結果に入っている資格情報を `signInWithCredential` に
渡す（もう一度ポップアップを開くと、直接のクリックから離れているので塞がれる）。

```
現在: ready: Promise<User>   一度掴んだら離さない
変更: currentUser を追い続け、getUid / getIdToken は常に「今の」ユーザーを見る
      初回の解決を待つための Promise は別に用意する
```

同時に `signIn()` を実装する。**2台目の分岐を最初から入れること。**

```
linkWithPopup(currentUser, googleProvider)
  ├ 成功                            → 匿名アカウントが昇格（uid そのまま）
  └ auth/credential-already-in-use  → その Google は既に別アカウントに紐づいている（2台目）
      → signInWithPopup で既存アカウントへログインし直す
        （この端末で作った空の匿名アカウントは捨てる）
```

**これを書かないと「2台目からログインできない」形でハマる。**
あとから足すのではなく最初から入れる。

確認: `linkWithPopup` を偽装して両方の分岐を通し、`getUid()` が正しい uid を返すこと。

## 手順3: 動線に繋ぐ【完了】

ボタンは「＋ 写真から3Dモデルを作成」、パネルは `src/ui/loginPanel.ts`。
ヘッドレスでは Firebase の認証エンドポイントを偽装して、匿名→パネル→やめる／失敗、
紐づき済み→そのまま作成、を確認してある。本物のポップアップは手順4。

```
[写真を選んで作る]
  作成には Google ログインが必要です        ← 押す前から見えている
        │
        ▼ タップ → 写真を選ぶ
        │
        ├─ ログイン済み ──────────→ そのまま作成開始
        │
        └─ 未ログイン
              ┌────────────────────────────────────┐
              │ 3D モデルの作成にはログインが必要です   │
              │ 選んだ写真はそのまま使われます          │
              │                                    │
              │   [Google でログイン]  [やめる]       │ ← 直接のクリック
              └────────────────────────────────────┘
                        │
                        ▼ ログイン成功
                 選んだ写真のまま自動で作成開始
```

押さえる点:

1. **押す前から必要だと分かる**（ボタン下の一行）
2. **写真を選び直させない。** 選んだ `File` はログインの間も保持し、成功したら
   自動で作成に進む。ログインのために作業がやり直しにならない
3. **ポップアップが確実に開く。**「Google でログイン」のタップは直接のクリック

これが出るのは**最初の1回だけ**。以降は uid が残るので、写真を選んだらそのまま始まる。

### 「ログイン先行」にしない理由

`[Google でログインして作る]` → ログイン → `[写真を選んで作る]` → 写真選択、
という順にすると実装は単純になるが、**ログイン成功後にファイル選択ダイアログを
自動で開けない。** ポップアップと同じ理由で、`await` を挟んだあとの
`input.click()` は Safari で塞がれる。結果タップが1回増える。

### ログアウトは置かない

匿名に戻す手段が無いため、ログアウトすると**それまでの生成履歴や許可リスト登録に
到達できなくなる**。置かないほうが安全。

### 利用者 ID の表示は変更不要

昇格しても uid は変わらないので、いまの表示のままでよい。

# PR ロジックマップ

## これは何のためか

コードを読んでレビューするのは負荷が高い。とくに自分が書いていないコードでは、
「何をしているか」を読み取るだけで時間を使い、「これで正しいか」を考える余力が残らない。

そこで、変更内容を**日本語で先に読めるようにし、コードは必要なときだけ開く**形にする。
レビュアーはまず日本語だけを上から追って全体を掴み、疑わしい箇所でコードを開く。

副次的な効果として、**書く側がバグを見つけやすくなる**。
処理を日本語で 1 本道に並べ直すと、対になっているべき処理の片方が欠けているといった抜けが目に見える。
実際、この形式で `onPointerDown` と `onPointerMove` を並べて書いたときに、
片方にだけ存在した判定の欠落（2 本目の指でも家具が動いてしまうバグ）が見つかっている。

## いつ使うか

- PR を作るとき（変更されたファイル・メソッドを対象にする）
- 既存コードの処理の流れを説明してほしいと言われたとき
- レビューを頼まれたとき

## 手順

1. `git diff main...HEAD` で変更範囲を把握する
2. 変更のあったメソッドを、下記の粒度で日本語に落とす
3. `assets/template.html` をコピーし、プレースホルダを埋めて本文を差し替える
4. Artifact ツールで公開する
5. PR の説明にアーティファクトの URL を貼る

## 粒度 ── ここが一番大事

**1 メソッドあたり数行**。目安は 5 行前後で、超えてもよいが 10 行を大きく超えるなら要約が足りない。

考え方はこう。コードのひとまとまり（連続する数行で 1 つの意味をなす部分）を、日本語 1 行にたたむ。
メインの処理は各メソッドの呼び出しを 1 行ずつ並べ、詳細も同じ要領で要約する。

**例**：`onPointerDown`（実際は 21 行）

```
- 1本目の指でなければ終わり
- 押した画面座標を控え、指の位置から光線を飛ばす
- 光線が家具に当たらなければ終わり
- 当たった家具を掴んだ状態にし、カメラ操作を止める
- 掴んだ点と家具の原点のズレを控える
```

`toNdc()` の呼び出しと `setFromCamera()` は「指の位置から光線を飛ばす」1 行にまとめている。
一方、早期リターンは処理の分岐点なので 1 行ずつ残す。ここを潰すと流れが読めなくなる。

### やりすぎの目安

- コード 1 行を日本語 1 行に置き換えている → 細かすぎる。それならコードを読めばよい
- メソッド全体が「〜を処理する」の 1 行になっている → 粗すぎる。流れが分からない

### 書き方

- **「なぜ」は原則書かない。** 判断の根拠が要る箇所だけ、行末に括弧で短く添える
  （例：「目標へ 12% だけ近づける（一気に切り替えるとチラつくため）」）
- **具体的な値は残す。** 「8px 未満なら」「10〜80 度に丸める」は、丸めずそのまま書く
- **変数名をそのまま使わない。** `draggingId` ではなく「掴んでいる家具」と書く。
  日本語として読めることが目的で、コードの逐語訳が目的ではない
- **メソッドは呼び出す側から並べる。** エントリポイント（`main.ts` など）を先頭に置くと、
  レビュアーが上から読むだけで全体構造を掴める

## テンプレートの使い方

`assets/template.html` に配色・フォント・折りたたみの仕組みが入っている。
CSS は書き直さず、本文の `<section class="file">` だけを差し替える。

埋めるプレースホルダ：

| 記号 | 入れるもの |
|---|---|
| `__TITLE__` | ブラウザタブ名。短い名前（例：操作ロジック 早見） |
| `__EYEBROW__` | 小見出し（例：リポジトリ名 / PR #12） |
| `__HEADING__` | 見出し |
| `__LEDE__` | 1〜2 文の説明 |

行に付けるクラス：

- `stop` … 早期リターン（灰色）
- `bug` … 問題のある箇所（赤字）
- 無印 … 通常の処理

コードを `<pre><code>` に入れるときは `<` と `&` のエスケープを忘れないこと。
忘れると HTML として解釈され、表示が壊れる。

## 対象から外してよいもの

読む必要がないものを載せると、それだけで「長い」という印象になり、
肝心の部分が読まれなくなる。以下は「対訳の対象外」として一覧で触れるだけでよい。

- `package.json` / ロックファイル
- 生成物（アイコン画像など）
- README やドキュメントの更新
- 設定ファイルの単純な値追加

設定ファイルは、値の羅列を 1 行ずつ日本語にしても価値が薄い。
判断が要る値（上限値、既定値の向きなど）だけを拾う。

## 気づいたことがあれば伝える

書いている途中でバグや不整合に気づいたら、それを黙って直さずに報告する。
アーティファクト内では該当行に `bug` クラスを付け、
チャット側で「何が起きるか」「どう直すか」を伝えて判断を仰ぐ。
